## Reproduction

Python 3.10 or later, no third-party packages, no key, no network. Per split (`development`, `validation`, `stress`):

```bash
python -m claimguard.run --input data/validation/claims.jsonl --output outputs/phase2/validation.jsonl \
  --explain --audit-log outputs/phase2/audit.jsonl
python src/evaluate.py --gold data/validation/expected_results.jsonl --pred outputs/phase2/validation.jsonl \
  --claims data/validation/claims.jsonl --output outputs/phase2/validation.metrics.json
python -m claimguard.evaluation.confusion --gold data/validation/expected_results.jsonl \
  --pred outputs/phase2/validation.jsonl --claims data/validation/claims.jsonl \
  --output outputs/phase2/validation.confusion.json --markdown outputs/phase2/validation.confusion.md
python -m claimguard.evaluation.summary --split validation --gold data/validation/expected_results.jsonl \
  --pred outputs/phase2/validation.jsonl --claims data/validation/claims.jsonl \
  --manifest outputs/phase2/validation.jsonl.manifest.json \
  --explanations outputs/phase2/validation.jsonl.explanations.jsonl \
  --output outputs/phase2/validation.summary.json --markdown outputs/phase2/validation.summary.md
```

Baseline for comparison: `python src/run_baseline.py --input data/validation/claims.jsonl --output outputs/phase2/validation.baseline.jsonl`, then the same `summary` command on it.

The official scorer, `src/evaluate.py`, stays authoritative. `confusion` and `summary` call its `score()` unchanged, so a run it rejects is rejected by them too, and their numbers cannot disagree with it.

## Data discipline

- **Splits.** The pack ships 400 development, 150 validation and 50 stress claims (docs/07). The mentor holds 200 more.
- **Which set is "the validation dataset (50 claims)"?** The book names 50 claims. The pack's validation split has 150, and its stress split has 50. Until the mentor answers, we report validation (150) as the headline and stress (50) separately, never pooled.
- **Label exposure.** We developed on development. Validation was scored during Phase 1 (status 1.00 is in the README since 1 Oct), so by docs/07's rule it is development feedback, not an untouched test set. No rule reads `expected_results.jsonl` or special-cases a claim ID, and CI forbids rules from reading the clock.
- **Where the labels come from.** The public labels were generated by the pack's reference engine (QA_REPORT.md). A perfect score shows we agree with that engine on the fictional rulebook. It is not independent validation and not payer approval. The mentor's held-out set is the real test.

## Metrics

### Definitions

| Metric | Definition |
|---|---|
| Issue precision, recall, F1 | The scorer's: a positive is a FAIL pair. UNABLE_TO_ASSESS is scored by status accuracy and the two abstention counts, not as an issue. |
| Macro F1 over rules | Mean of the 15 per-rule issue F1. A rule with no expected and no predicted FAIL has an undefined F1: it is listed, never counted as 0 or 1 (docs/07). |
| Macro F1 over categories | tp, fp and fn pooled inside each category, F1 per category, then the mean. |
| Categories | `claimguard/evaluation/categories.json`, a team proposal from the book's own words for what the engine must detect: **missing** (R001, R008, R010), **inconsistent** (R002, R004, R007, R012, R015), **duplicate** (R006), **unsupported** (R003, R005, R009, R011, R013, R014). `rules/rules.json` has no category field. |
| False-alarm rate (pairs) | The scorer's: predicted FAIL among pairs whose expected status is not FAIL. |
| False-alarm claims | Claims with no expected FAIL that get a predicted FAIL. |
| Clean claims sent to a reviewer | Claims whose 15 expected results are all PASS or NOT_APPLICABLE that get any FAIL, UNABLE_TO_ASSESS or NOT_IMPLEMENTED. This is the book's "preserving valid claims": a valid claim the officer must look at for nothing. |
| Claim exact match | Claims with all 15 statuses correct (docs/07). |
| Latency | Wall time of `claimguard.run`, from its manifest (`duration_ms`), which `summary` refuses unless the manifest's results hash matches the scored file. |

## Held-out set (mentor)

The brief: "Evaluate on the provided data, then on a mentor-held set. Report false alarms, missed issues and uncertainty handling separately." The mentor holds 200 claims and their labels; we never see the labels.

**Protocol**, from the frozen commit, once:
1. `python -m claimguard.run --complete --input <held-out claims.jsonl> --output outputs/heldout.jsonl --explain --audit-log outputs/heldout_audit.jsonl`. `--complete` keeps the run scorable if any claim fails ingestion (DEC-013), subject to the mentor's answer.
2. The mentor scores `outputs/heldout.jsonl` with `src/evaluate.py` and, if they agree, `python -m claimguard.evaluation.summary`.
3. The results go below, unchanged, with the number of claims completed (from the manifest's `completed_rejected`) and every rule the mentor reports as wrong.

| held-out | Value |
|---|---|
| Claims · completed at ingestion | to fill |
| Status accuracy | to fill |
| Macro F1 over rules · over categories | to fill |
| False alarms (false FAIL pairs · false-alarm claims) | to fill |
| Missed issues (FAIL pairs we did not report) | to fill |
| Uncertainty: false abstentions · missed abstentions | to fill |

No rule may be changed after the held-out run to fit it (docs/07: never tune on the hidden labels).

## Error analysis

The engine disagrees with the gold on **no** claim-rule pair in any public split. So instead of errors, these are the five cases most likely to break on the mentor's held-out set, each checked on our output:

| # | Claim · rule | What the engine does | Why it is hard |
|---|---|---|---|
| 1 | CG-B39790AC3604 · R008, R009 | R008 FAIL "Required authorization ID missing" (L1); R009 UNABLE_TO_ASSESS "Cannot inspect authorization without an ID" | One missing value must give a FAIL in one rule and an abstention in the next, never two FAILs. R008 and R009 share one predicate (DEC-007). |
| 2 | CG-87A4E9122143 · R009 | FAIL "Authorization status mismatch", evidence down to `/authorizations/0/status` | The gold shows only 2 of R009's 6 failure reasons; the other 4 wordings are our decision (DEC-005, DEC-006). |
| 3 | CG-DE0F653AF4D4 · R013 | FAIL "Quantity must be a positive integer" on quantity 1.5 | `2.0` passes and `true` fails: decisions the gold never tests (DEC-001, DEC-002). |
| 4 | CG-27BFD8541DEB · R003 | PASS, with every service date inside the coverage window, boundaries included | The same claim with `coverage.status` null must give UNABLE_TO_ASSESS, never PASS: unknown is not clean (DEC-004). |
| 5 | CG-BC77D328F1A2 (validation) with one date written `20260525`, or one unexpected key | Rejected at ingestion; the run exits 2 and lists it in the manifest | **The scorer then rejects the whole run: 15 missing pairs.** One malformed held-out claim would void every other result. `python -m claimguard.run --complete` (Role B) gives such a claim 15 UNABLE_TO_ASSESS results instead. On the unexpected-key case, the official scorer then accepts the run with status accuracy 0.993 and 15 false abstentions. Using it on the held-out run waits on the mentor (open question 1 in `docs/DECISIONS.md`); our default is to use it and disclose it. |

Robustness checks outside the public labels:
- **Malformed FHIR:** `tests/test_fhir.py` has 14 structural cases, sidecar mismatches, a 10-input malformed matrix (truncated JSON, deep nesting, `{}`, a string, `entry` not a list, null entry, entry without resource, not a Bundle, no Patient, invalid UTF-8) and a 500-mutation fuzz test. Each bad bundle is exactly one ingestion error, and the good bundles in the same file are still checked.
- **Seeded mutation sweeps over JSONL and CSV** (`tests/test_ingest_fuzz.py`): every development claim gets 1 to 3 random changes, and 600 CSV cells are mutated. Ingestion never raises. All 88 mutated JSONL claims that pass ingestion run all 15 rules in strict mode, and every evidence value resolves. With `--complete` the run has exactly one result per claim and rule. The sweep found one real crash, now fixed: a lone surrogate (`"\ud800"`) in a string killed the results write (DEC-013).
- A Phase 1 crash sweep ran every rule on 54,735 mutated claims. It found 3,675 crashes of two kinds (huge amounts, non-object entries), fixed in DEC-012 and covered by tests in `tests/test_r007.py`, `test_r009.py`, `test_r010.py` and `test_r012.py`.

**Confidence.** The book asks for a "confidence score". Every result carries `confidence: null` with `confidence_kind: not_probabilistic`, because the rules are deterministic and the pack's scorer refuses any number on a deterministic result ("Deterministic confidence must be null"). Low confidence is therefore shown as an abstention: UNABLE_TO_ASSESS, or NOT_IMPLEMENTED. Routing escalates these. A live model's self-reported score would be labelled `uncalibrated` and never used for routing (docs/05).

## Human review and security

Covered in full by the privacy and security note, `docs/PRIVACY_SECURITY.md`: the threat model with a test for every control, access control, least privilege, auditability, and the tamper demonstration (`python -m claimguard.audit.tamper_demo`). The main tests:
- `tests/test_routing.py`, `tests/test_correction.py`, `tests/test_ui_e2e.py`: 18 browser tests pass in Chrome, including the decision flow and hostile text that never runs.
- `tests/test_audit_chain.py`, `tests/test_rbac_and_secrets.py`, `tests/test_injection.py`, `tests/test_fhir.py`.

**Explicit human approval is enforced, not only shown.** `python -m claimguard.review.gate` reads the verified audit chain and the actor directory, judges each claim on its latest version, and exits non-zero while any claim is blocked. With no decisions recorded it reports 136 ready and 264 blocked on development, the same as the page's dashboard. Its states are the page's own, kept equal by a Node test (`tests/test_gate.py`, `tests/test_ui_core.py`). Each flagged finding names its triggers (low confidence, high severity, proven issue), the words of the challenge's Phase 2. `python -m claimguard.review.feedback` summarizes the recorded decisions and lists the rules reviewers often dismiss.

**A corrected claim is reviewed on its new version.** `python -m claimguard.review.correct` reruns all 15 rules on a corrected version. If that version still has findings, the page shows "Deciding on version N" with that version's findings, checks and data. `python -m claimguard.ui.decisions --corrections` accepts decisions taken on that version and refuses any taken on an older one. The gate then judges the claim on it. Earlier, such a claim stayed "rechecked" and could never be approved (`test_gate.test_a_corrected_version_that_still_flags_is_decided_on_that_version`).

A malformed claim in the claims file no longer stops the review tools. The page lists it under "Rejected at ingestion", decisions on the other claims are appended, and a decision on it is refused with a reason (`tests/test_rejected_claims.py`, DEC-013).

Full suite at the frozen tag: 510 tests, OK, including the 19 browser end-to-end tests.

## Limitations

- **Synthetic and fictional.** All claims, policies and codes are invented. A perfect score means we agree with the pack's reference engine; it is no evidence of production readiness or of any denial reduction.
- **Small positive counts.** Validation has 117 FAIL pairs. R006 has 10, and some rules have fewer. One error would move a rule's F1 a lot, which is why per-rule and per-category figures are shown, not only the mean.
- **Undefined F1 on stress** for 9 rules and the duplicate category; they are listed, not averaged in.
- **The category grouping is ours**, pending the mentor's confirmation. Macro F1 over rules does not depend on it.
- **A rejected held-out claim** (case 5) voids a scored run unless the run uses `--complete`. With `--complete` its 15 results are UNABLE_TO_ASSESS and count as abstentions. Whether to use it on the held-out run waits on the mentor (DEC-013); our default is to use it and disclose it.
- **Mock model only.** No live-model quality, latency or cost has been measured, and the clinical-advice guard is not proven against a real model. The mock's own scorecard shows its limits: no verification step, and the missing field not named on 3 of 5 uncertainty cases.
- **Latency** is one laptop, one process, mock explanations.
- **The scorer checks statuses and evidence values, not meaning.** A correct status for the wrong reason would score.
